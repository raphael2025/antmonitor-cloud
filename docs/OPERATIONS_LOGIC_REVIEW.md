## 1. 现场用途

云端最实用的工作是发现整场失联、场地扫描停滞和大范围掉算力，并及时通知值班人员。
场地断电时，本地监控本身可能停止；这时云端通知是否可靠，比多显示一项数字更影响处置。

| 功能 | 实用性与边界 |
|---|---|
| 全网与各场地摘要、趋势 | 适合老板和值班经理找出异常场地。采样新鲜度、数据缺失和部分合计必须保留区别。 |
| 客户实时、周期平均、耗电估算 | 适合趋势对照和初步核对；客户由矿工名归组，监控估算不等于电表或合同结算。 |
| 主动上报与 AMC1 接入 | 地址与 token 等信息放在一份接入包中，场地网页/命令界面整段粘贴。AMC1 是编码，不是加密。 |
| 失联/停滞/骤降/掉线规模通知 | 核心能力。本次重点验证触发、恢复、服务商确认、失败补发及配置变化。 |
| 撤销、删除、恢复场地 | 有实际用途，应按场地 ID 操作。删除会丢掉对应历史，恢复记录后需生成新接入信息。 |
| viewer / admin | 当前是全网角色权限。viewer 能读所有场地和客户分组，不是客户隔离门户。 |
| 多语言、日间/夜间 | 有助于不同值班环境，属于使用便利性，不增加故障处理步骤。 |

依据：`server.py`、`collector.py`、`notify.py`、`auth.py`、`db.py` 和对应测试。
已有采样、功率、电量、平均算力与跨场地口径见 [数据逻辑审计](DATA_LOGIC_AUDIT.md)。

## 2. 本次复现并修复的通知缺陷

### A. 算力没有恢复，滚动基线却让告警消失

最小反例：算力从 100 降到 50 后持续不变。原程序使用 45～90 分钟前的滚动均值做恢复判断；
当历史窗口也降到 50 时，会错误通知“恢复”，尽管实际仍只有原算力的一半。

现在每次骤降事件保留触发时的原始基线。恢复阈值一直对照该基线，缺测不触发恢复。
例如骤降阈值 30%，原基线 100，恢复需回升至 85，而不是随着低算力持续时间自动降低要求。

### B. 首次发送失败后不再尝试

原程序在发送前就占用冷却记录，并推进状态；如果失联通知恰好网络失败，持续失联期间没有新状态跳变，
该通知会永久丢失。

现在当前事件的未送达通道进入内存重试队列，间隔为 60、120、240、480 秒，之后最高 900 秒；
由采集循环在到期后执行，循环延迟也会使实际发送推迟。成功通道不重复补发，每个通道独立记录结果。
恢复或相反状态会取消过期消息，删除场地会清理待发事件。
关闭通知表示暂停投递；重新启用时，对仍成立且尚未送达的当前事件继续处理，不补发已经恢复的旧故障。

队列按场地和三类事件组限制，不无限累积历史消息。它保存在进程内，服务重启会丢失未送达队列；
现有启动首轮只建立状态基线的策略仍保留，没有宣称提供重启后可靠投递。

### C. HTTP 可达被当成业务发送成功

原程序只看 HTTP 返回是否成功。企业微信/钉钉 HTTP 200 但 JSON `errcode` 非零时，测试仍可能显示成功。

现在 Telegram 要求 JSON `ok` 为 true，企业微信/钉钉要求整数 `errcode` 为 0；
重定向和业务错误不算成功。自定义 raw Webhook 维持 HTTP 2xx 接收契约，可以返回空响应体。
服务商确认接收也不等于某个值班人员已经阅读消息。

## 3. 运维说明修正

部署文档原先将云端数据描述为“可以重新积累，不算关键”。实际历史、通知记录、改名、删除记录及凭据
不能靠下一次上报全部恢复。本次改为数据库在线备份，并明确保存配置覆盖层与所用证书/私钥。
没有新增需要用户逐项配置的通知表单。

## 4. 验证及限制

测试使用内存 SQLite、模拟时钟和模拟通道，不发送真实 Telegram、Webhook 或邮件。
持续低算力的误恢复反例使用真实历史序列；补发测试包括多个通道部分成功、退避、冷却、
相反状态、场地删除、关闭/重开及业务错误码。

本轮完整测试：**279 项通过、6 个子测试通过**；其中新增通知专项 **49 项**。
暂停期间恢复、随后再次故障、仅恢复以及双通道部分成功另经独立反例复核。

```bash
python -m pytest -q
```

真实服务商可达性、机器人群配置、生产设备固件和现场电表未在本轮访问或验收。
